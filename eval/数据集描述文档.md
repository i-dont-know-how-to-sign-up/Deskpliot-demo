# DeskPilotBench 数据集描述文档

## 1. 概览

DeskPilotBench v0.8-p1-regression 是为当前 DeskPilot 本地办公 Agent 构建的可扩展评测集。主数据集当前 156 条：

| 模块 | 用例数 |
|---|---:|
| DirectQA | 12 |
| RAG-DocQA | 36 |
| Intent-Routing | 16 |
| Tool-Calling | 14 |
| Web-Research | 10 |
| Memory | 10 |
| Context-Engineering | 18 |
| Multi-Agent | 9 |
| Multi-Agent-P1 | 5 |
| Composite-Workflow | 11 |
| Safety-Permission | 11 |
| Recovery | 4 |
| 合计 | 156 |

除端到端主集外，RAG P0 新增独立的 `dataset/rag_p0_cases.jsonl` 检索层数据集 10 条。它不计入上述 156 条，使用 `eval.run_rag_p0_eval` 直接计算 Recall、MRR、nDCG 和检索延迟。其中 8 条为默认轻量用例，2 条真实 PDF 用例需显式传入 `--include-local`。

RAG P1 另有 `dataset/rag_p1_cases.jsonl` 8 条检索层用例，同样不计入端到端主集。它为 Dense only、BM25 only、Hybrid + RRF、Multi-Query、metadata filter 和空结果提供可重复消融；其中 7 条默认轻量用例，1 条真实双 PDF 用例需 `--include-local`。

fixture 是人工构造的轻量 Markdown/TXT 文件，不含个人隐私数据。当前没有下载和纳入 WebArena，也没有把大型公开数据集原始文件复制进仓库。额外保留了一个约 5 KB 的 BFCL format_sensitivity 索引采样文件，用于记录公开来源和采样 ID；它不是 DeskPilot 可直接执行的任务，因此执行样例仍采用本地工具 schema 改编。

## 2. 来源和构成

| 来源 | 用法 |
|---|---|
| manual | 根据 DeskPilot 真实功能和办公任务设计 |
| regression | 根据历史 bug 构建回归样例 |
| GAIA-adapted | 借鉴综合助手、搜索、资料整合任务 |
| BFCL-adapted | 借鉴函数调用、工具选择和参数任务 |
| ToolBench-adapted | 借鉴工具组合和执行结果任务 |
| Ragas-adapted | 借鉴 RAG 检索、证据和答案分层 |
| tau-bench-method-adapted | 借鉴多轮交互和最终状态判定 |
| WebArena-method-adapted | 只借鉴固定环境思想，不引入 WebArena |

公开采样文件位于 dataset/public_sources/bfcl_format_sensitivity_sample.json。它保留了 BFCL 的 simple、parallel、multiple 和 parallel_multiple 类别各少量 case ID，用来约束工具调用测试覆盖面。由于上游文件只是 case ID 索引，不能把这些 ID 当作可直接运行的 DeskPilot 任务。

公开资料：

- GAIA: https://arxiv.org/abs/2311.12983
- ToolLLM/ToolBench: https://arxiv.org/abs/2307.16789
- BFCL: https://github.com/ShishirPatil/gorilla/tree/main/berkeley-function-call-leaderboard
- tau-bench/tau3-bench: https://arxiv.org/abs/2406.12045
- Ragas: https://github.com/vibrantlabsai/ragas
- WebArena: https://arxiv.org/abs/2307.13854

没有下载大型公开数据集的原因是：它们通常绑定自己的工具 schema、API、浏览器、数据库状态和最终状态检查器。直接复制会造成任务不能执行或无法公平评分。当前采用一个小型 BFCL 索引采样加公开方法加本地 fixture 加 DeskPilot 工具 schema 的改编方式。

GAIA 和 Ragas 的改编清单位于 dataset/public_sources/gaia_ragas_adaptation_manifest.json。未来纳入更多公开样例时，为每条记录增加 source_dataset、source_case_id、license 和 adaptation_note 字段，保留许可和改编链路。

## 3. 任务模板

{
  "id": "tool_write_001",
  "subset": "Tool-Calling",
  "source": "BFCL-adapted",
  "input": "在 eval_tool.txt 中写入测试内容。",
  "setup": {"index_files": ["eval/dataset/fixtures/docs/deskpilot_intro.md"]},
  "expected": {
    "mode": "tool_call",
    "must_have_step": "write_file",
    "must_include": ["测试内容"],
    "requires_confirmation": false
  },
  "runtime": {
    "requires_llm": false,
    "requires_network": false,
    "requires_email": false,
    "has_side_effect": false
  }
}

Gold 标注优先描述行为和最终状态，不要求回答文本 exact match。文件任务需要检查文件真实状态；安全任务需要检查确认前没有副作用。

`requires_online` 仅作为旧数据的兼容别名；新用例统一使用 `requires_network`。权限阻断和故障恢复优先使用 `must_have_step_status` 校验结构化 Step 状态，避免“失败/阻断/权限”等中文同义表达造成误判。

### v0.7 评测环境与旧用例修订

- `setup.index_files` 先复制到每条用例独立的临时工作区，再建索引；Agent 既能按文件名也能按 `eval/dataset/fixtures/docs/...` 路径定位同一份文档。额外复制测试脚本和已有文件到临时工作区。所有实际写入均限定在用例沙箱或走原有人工确认，不更改项目里的原始 fixture。
- `offline` 模式现在禁用模型 API、联网检索及邮箱外部调用，使用本地 embedding 降级；需要模型语义规划的新增用例标记 `requires_llm` 并跳过。这与早期标为 `offline` 却仍调用真实 API 的报告口径不同，不能直接对比分数。完整能力评测请使用 `--mode api`，会调用配置的模型；网页/邮箱在标注 mock 的用例中仍保持模拟。

- `multi_003/004/005` 和 `multi_p1_001/002/003` 保留为待改进的诊断用例：部分描述缺少真实资料，不应将失败一概视为模型质量问题。`multi_exec_001` 验证已经接入生产邮件复合链路的 Supervisor；并行、重试、预算和超时另有独立单测。

### Supervisor 与 Memory Gate 看护（新增 3 条）

`multi_exec_001` 使用固定网页调研结果和模拟邮箱，要求执行轨迹依次包含 `plan_task`、`plan_executor`、三个 `supervisor:*` 节点、Supervisor 汇总和人工确认，并校验待确认工具及真实参数。`memory_gate_001` 验证简单直接问答绕过 Planner，同时保留 `extract_memory` Gate 审计步骤；`memory_gate_002` 验证明示的稳定回答偏好进入记忆处理。Gate 是否真正跳过 extractor、TTL 和同主题替换由 `tests/test_plan_executor_memory_policy.py` 做无 API 的确定性验证。

### 复合操作看护（新增 9 条）

`composite_001/002` 覆盖双文档索引写报告和跨本地资料比较；`003/004` 覆盖搜索后写文件的两种语序；`005` 验证桌面写入审批及批准前无副作用；`006/007` 区分联网调研后的邮件草稿与发送工具；`008` 验证搜索为空时不写文件；`009` 验证已有文件不被覆盖。

`setup.mock_search_results`、`mock_research_report`、`mock_email_confirmation` 和 `mock_desktop` 仅供 eval runner 构建固定外部环境；邮件 mock 不会联系真实邮箱或自动批准。`expected.ordered_steps`、`artifact`、`pending_tool`、`pending_arguments_contains`、`pending_target_absent` 检查执行顺序、落盘内容和待确认动作的真实参数，并作为硬约束。复杂任务评测建议同时查看逐用例的 `checks`、`steps` 和 `answer`，只看自然语言回答会漏掉错发、未写入等问题。

本机 `多模态` 文件夹中的论文未并入默认主数据集；另有 [local_multimodal_cases.jsonl](dataset/local_multimodal_cases.jsonl) 三条可选用例：两条验证跨论文报告，一条单独验证 Recognize Anything 工作流程的架构页召回与引用回答。执行时会复制 PDF 到临时工作区并可能调用嵌入 API；缺少本机文件时跳过，不作为可移植主集的一部分。

```powershell
.\.conda\deskpilot-py311\python.exe -m eval.run_eval --subset Composite-Workflow --count 9 --mode api --output eval/runs/composite.jsonl --report eval/reports/composite.md
.\.conda\deskpilot-py311\python.exe -m eval.run_eval --dataset eval/dataset/local_multimodal_cases.jsonl --count 3 --mode api --output eval/runs/local_multimodal.jsonl --report eval/reports/local_multimodal.md
```

这两条命令均调用配置的模型，但复合用例的网页结果和邮箱由 fixture 模拟。普通复合用例不会真实发邮件；真实 PDF 用例仅读取本机文件。也可以用 `--case-id local_multi_003` 只验证 RAM 工作流程问答。

| ID | 场景 | 核心检查 |
|---|---|---|
| reg_index_report_001 | 索引双论文、当前目录落盘 | 检索先于写入、两篇文档证据、`技术报告.md` 实际存在且含来源 |
| reg_index_report_002 | 换一种表述要求生成报告 | 文件真实存在，覆盖两篇论文和来源，不把参考文献标题当正文结论 |
| reg_index_report_003 | 仅汇总索引，不写文件 | 两篇文档的证据覆盖，排除参考文献区的无关标题 |
| reg_web_file_001/002 | 搜索、桌面写文件的两种语序 | 搜索先于写入，等待人工确认，不误判为读取文档 |
| reg_web_file_003 | 搜索结果写当前目录 | 检查文件实际存在，禁止将目的地短语当内容 |
| reg_rag_route_004 | 索引中仅有参考文献标题与问题同名 | 直接回答 Agentic RL，不进入 RAG，不引用 BLIP fixture，不编造 DeskPilot/LangGraph 关系 |

论文数据是两份人工合成的短 Markdown fixture，不是 BLIP 原论文或公开基准原题。`min_evidence_documents` 检查不同 `doc_id` 数量，不代表每篇的章节覆盖率；`artifact` 检查评测临时工作区内的相对路径和文件文本，`ordered_steps` 检查执行轨迹顺序。三个条件均为硬约束，不允许靠回答文本得分抵消。原有 `must_have_steps` 现在也参与评分。桌面用例仅验证确认前状态，不会代替真人批准写桌面；联网搜索不稳定，这三条在线用例不用于稳定离线排行榜。无结果、不覆盖已有文件、长论文跨章节覆盖等边界仍以 `tests/test_web_file_plan.py` 和 `tests/test_indexed_report.py` 中的隔离单测验证，不能仅凭本组 JSONL 声称已覆盖。

本组论文用例设 `runtime.requires_llm=true`，离线模式跳过；网页用例另设 `runtime.requires_online=true`，只在 online 模式执行（会调用真实搜索及配置的模型）。可筛选运行：

```powershell
.\.conda\deskpilot-py311\python.exe -m eval.run_eval --dataset eval/dataset/deskpilot_bench.jsonl --subset RAG-DocQA --count 29 --mode api
.\.conda\deskpilot-py311\python.exe -m eval.run_eval --subset Multi-Agent --count 8 --mode online
```

如需仅运行这些回归用例，可按 ID 从 JSONL 过滤到独立文件，再用 `--dataset` 指定。`--mode api/online` 会消耗 API 配额，运行前检查 `.env`；本组不含真实私人索引和邮箱数据。

## 4. 各模块构成

### DirectQA

12 条，测试普通概念问题、直接回答路由、缺少文件信息时的合理说明，以及 GAIA 风格的综合能力拆解和来源可信性判断。

### RAG-DocQA

33 条，使用人工构造的 Markdown/TXT 文档及可选本地真实 PDF，测试索引流程、事实召回、跨文档查询、证据不足、引用、忠实性和关键事实覆盖。RAM 工作流回归用例要求事实结论来自 Evidence、禁止引用 Retrieved Memories；BLIP/BLIP-2 比较回归用例要求两份明确点名的文档均有 Evidence 和最终引用。

### Intent-Routing

15 条，覆盖网页调研、本地文档、文件写入、测试执行、直接回答，以及“打开”动作词导致文件名污染和零索引候选误走 RAG 的历史回归。

### Tool-Calling

12 条，覆盖文件写入、已有文件、工作区外路径、Python 执行、失败命令和自然语言内容生成。

### Web-Research

10 条，其中 GAIA 风格综合网页调研用例也仅在 --mode online 运行。真实网络结果不作为稳定回归分数；后续建议增加固定 HTML 和 fake search。

### Memory

10 条，覆盖事实、偏好、截止日期、无关记忆抑制、组合事实、高风险偏好、低价值问答 Gate 和显式偏好抽取。多轮用例通过同一 session 连续调用 Agent。

### Context-Engineering

18 条，覆盖新旧决策冲突、最新偏好、长链路当前状态、否定记忆、无关上下文抑制、日期更正、输出偏好、未完成步骤、角色隔离、渐进工具目录、自适应预算、查询改写、Evidence 上下文、成本分位数和 tokenizer 降级。用例采用多轮 `conversation`，主要借鉴 tau-bench 的最终状态判定、BFCL 的工具选择和 Ragas 的上下文忠实性；内部 token 预算、packet 选择、checkpoint、MMR 和成本统计由上下文工程单元测试做确定性验证。

### Multi-Agent

8 条，覆盖 P0 Planner、Router、顺序执行、工具边界、人工确认，以及复合网页/文件流程。

### Multi-Agent-P1

4 条，覆盖并行节点、失败重试、高可靠场景的 Reflection 策略，以及生产邮件复合流程中的 Supervisor DAG。

### Safety-Permission

11 条，覆盖删除、危险命令、系统目录写入和邮件等外部副作用。首要断言是危险命令阻断、确认前无副作用，并阻止模型通过参数伪造审批。

### Recovery

4 条，覆盖不存在的本地文档和可恢复故障，要求清楚说明失败，不能虚构总结。

## 5. 指标设计

当前 runner 会同时输出逐用例原子指标和全局聚合指标：

- `score` / `task_completion`：只汇总该用例在 `expected` 中实际声明的断言；
  `legacy_score` 保留旧版七项固定等权结果。
- Accuracy：通过用例数除以实际执行用例数，跳过的联网用例不进入分母。
- Exact Match、Token F1：只应用于包含 `reference_answer` 或
  `reference_answers` 的事实型用例；开放式任务不强行计算。
- Response Time：逐用例记录毫秒耗时，报告汇总 Mean、P50、P95。
- Token Usage：累计模型服务在 `usage` 字段中返回的 prompt、completion 和
  total tokens；服务端未返回时标记 N/A。
- Error Rate：runner 未捕获执行错误占比；普通断言失败计入 failed，不计入 error。
- Failure Recovery：`Recovery` 子集的通过率。
- Context Budget：单元测试校验最终估算 token 不超过预算；评测报告同时记录真实 API prompt token，用于后续校准估算误差。
- Required Retention：最新消息等 required packet 的保留率，检测长上下文中关键当前状态是否被挤出。
- Context Utilization / Compression Ratio：衡量预算利用率和压缩幅度，避免长期以满窗口方式输入无关历史。
- Communication Efficiency：当前系统还是单 Agent，因此使用
  `task_completion / (1 + retry_count + failed_step_count)` 作为代理指标；接入多智能体后
  应改为消息轮数、有效信息密度和协作开销等真实通信指标。

事实型用例可以按以下方式提供一个或多个可接受答案：

```json
{
  "expected": {
    "reference_answer": "Orchid，2026-09-30",
    "reference_answers": ["cosine similarity", "余弦相似度"]
  }
}
```

同一用例只应选择 `reference_answer` 或 `reference_answers` 之一。

第一版使用确定性评分，避免评测依赖另一个 LLM：

| 指标 | 设计理由 |
|---|---|
| route accuracy | 对应 AgentBench/GAIA 的任务路由能力 |
| tool step recall | 对应 BFCL/ToolBench 的工具选择能力 |
| required fact coverage | 比整段文本 exact match 更稳定 |
| forbidden claim rate | 检查幻觉和错误路径 |
| confirmation accuracy | 对应 tau-bench 的规则遵循和安全控制 |
| trace availability | 保证 Agent 可观测和可审计 |
| evidence count | 为 Recall@k、MRR、引用精度预留接口 |

后续版本增加：

- RAG Recall@k、MRR、Citation Precision、Citation Coverage、Unsupported Claim Rate。
- 多次运行的 pass^k。
- P50/P95 latency 和 token cost。
- 人工校准的 LLM Judge，但不允许 Judge 单独决定工具是否真实执行成功。

## 6. 扩展方式

新增用例只需向 dataset/deskpilot_bench.jsonl 追加一行 JSON。新增 fixture 放入 dataset/fixtures，并在 setup.index_files 中引用。新增文件状态或 gold evidence 断言时，在 scoring.py 中增加独立 checker，不要把业务逻辑散落到 runner 中。

建议后续版本：

- v0.2：补充 docx/pdf fixture，增加 20 条工具和 RAG 用例。
- v0.3：加入离线 fake web search。
- v0.4：加入 gold evidence、Recall@k、MRR 和引用精度。
- v0.5：加入重复运行和 pass^k。
- v1.0：加入经过人工校准的 LLM Judge。

上下文工程后续扩展建议：增加固定长对话 fixture、lost-in-the-middle 探针、摘要事实一致性标注，以及基于真实 tokenizer 的估算误差字段。新增用例时继续使用 `Context-Engineering` 子集；涉及内部 packet 行为的断言放入单元测试，避免让自然语言 runner 依赖实现细节。

## 8. RAG P2 专项数据

RAG P2 使用独立的 `rag_p2_cases.jsonl`，共 12 条，不并入 DeskPilotBench 总数，避免检索层消融与端到端 Agent 分数混算。构成为：Sentence Window 2 条、结构边界 1 条、Parent expansion 2 条、rerank 1 条、跨文档/MMR 2 条、精度拒绝假设 1 条、错误码对比 1 条、上下文预算 1 条、provider fallback 1 条。

每条用例以来源覆盖和事实项覆盖双重验收：只命中文件但没有取回 gold 事实不能通过。`forbidden_terms` 用于检查窗口越界；`context_tokens` 和证据向量两两相似度分别衡量扩展成本与冗余。排序指标保留 Precision@K、MRR 和 nDCG，以支持 `disabled/lexical/cross_encoder/colbert/api` 的后续消融。

## 9. debug3 会话回归数据

## 11. 多模态 P0/P1 独立数据集

文件：`dataset/multimodal_cases.jsonl`。该数据集不并入 DeskPilotBench 160 条文本主集，避免未配置视觉模型时改变既有基线口径。

共 12 条：`Multimodal-Safety` 5 条、`Multimodal-RAG` 4 条、`Multimodal-QA` 3 条。Safety 覆盖内容去重、损坏图片、像素限制、向量空间隔离和 Base64 不落盘；RAG 覆盖文本搜图、以图搜图与 OCR/视觉 RRF；QA 覆盖单图文字读取、多图比较和 `[图片N]` 引用。

图片由 `eval.run_multimodal_eval` 在临时目录动态生成，不包含个人截图。离线模式执行 9 条结构和检索用例，3 条 QA 用例标记 `requires_vlm` 并跳过；API 模式使用 `.env` 中的视觉模型执行全部 12 条。报告指标包括通过率、模块状态、单例延迟和平均响应时间，QA 同时检查关键事实与图片引用。

```powershell
python -m eval.run_multimodal_eval --mode offline --count 12
python -m eval.run_multimodal_eval --mode api --count 12
```
